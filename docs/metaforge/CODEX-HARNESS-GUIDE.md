## Start here

**The main Codex harness implementation is in `codex-rs/core/`.** At this snapshot, the top-level `codex-cli/` directory primarily packages and launches the Rust executable through npm.

If you read one file first, choose [core/src/session/turn.rs](https://github.com/openai/codex/blob/c260087efe8cc6dcc0526e7018ae9e0e3fc134e3/codex-rs/core/src/session/turn.rs). Its `run_turn()` function is a key entry point for understanding the model → tool → feedback → next model request loop.

The reviewed checkout contained 9,439 Git-tracked files. This guide explains root-level entries and then follows the harness implementation; it is not a file-by-file audit of every dependency, fixture, and test. Paths and call relationships can change in later versions.

## 1. What is the harness?

The model proposes what to do next. The harness:

- Supplies tasks, history, instructions, and tool definitions to the model.
- Receives tool calls, executes commands, and changes files.
- Handles permissions, sandboxing, timeouts, and output truncation.
- Returns execution results to the model and continues the loop.
- Persists sessions and supports resumption and context compaction.

The harness is the execution system around the model. It is neither the model weights nor just the terminal interface. See the [upstream explanation of Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform).

For source navigation, separate four layers:

1. **User-facing entry points:** CLI, terminal UI, and SDKs.
2. **Services and agent core:** requests, sessions, model interaction, and execution loops.
3. **Tools and execution environments:** commands, file changes, permissions, and sandboxes.
4. **Supporting infrastructure:** history, protocols, configuration, builds, and tests.

### 3.2 Similar names with different meanings

- `codex-cli/` is npm packaging; `codex-rs/cli/` is the Rust CLI implementation.
- `exec/` runs an agent task; `exec-server/` provides lower-level command and filesystem execution.
- `core/` manages execution; `tui/` primarily manages terminal presentation and interaction.
- Root `tools/` contains development utilities; `core/src/tools/` is central to the agent tool system.
- Root `patches/` contains dependency maintenance patches; `apply-patch/` applies patches at runtime.

Two distinctions matter for empirical studies.

**Collected output is not necessarily model-visible output.** `ExecCommandToolOutput` handles logging, model responses, and Code Mode results under output budgets. Earlier collection layers can also limit retained output. A field named `raw_output` does not necessarily contain every byte produced by the process.

Separate what the process produced, what the executor retained, what the tool returned to the model, and what the UI or logs displayed.

**Counting `apply_patch` is insufficient.** Shell commands and Python scripts can also change files. Inspect actual workspace state, and do not treat an attempted edit as a successful modification without evidence.

## 5. Connecting the components

The following is a simplified reading map. It omits compatibility paths, concurrency, retries, and extensions; it is not a guarantee that every entry point follows one identical serial stack.

```text
CLI / TUI / SDK
       ↓
app-server: thread and turn requests
       ↓
core/session/turn.rs: prepare context and advance the task
       ↓
core/client.rs: request model output
       ↓
model proposes a tool call
       ↓
tools/router + registry: dispatch and manage execution
       ↓
exec_command / apply_patch / other handlers
       ↓
executor runs commands or changes files
       ↓
format and truncate results; record history
       ↓
request the model again or finish the turn
```

A user turn can contain many model requests and tool calls. A single model response does not imply task completion.

Entry points include [cli/src/main.rs](https://github.com/openai/codex/blob/c260087efe8cc6dcc0526e7018ae9e0e3fc134e3/codex-rs/cli/src/main.rs), [app-server/src/message_processor.rs](https://github.com/openai/codex/blob/c260087efe8cc6dcc0526e7018ae9e0e3fc134e3/codex-rs/app-server/src/message_processor.rs), [turn_processor.rs](https://github.com/openai/codex/blob/c260087efe8cc6dcc0526e7018ae9e0e3fc134e3/codex-rs/app-server/src/request_processors/turn_processor.rs), and [core/src/tasks/regular.rs](https://github.com/openai/codex/blob/c260087efe8cc6dcc0526e7018ae9e0e3fc134e3/codex-rs/core/src/tasks/regular.rs).

## 6. Studying how tests influence patches

### 6.1 Follow the complete feedback path

Study this sequence rather than only counting test commands:

> Actual test execution → returned output → model-visible feedback → subsequent model output → actual file changes.

Read `session/turn.rs` for feedback propagation; `exec_command.rs` and `process_manager.rs` for execution and completion; `tools/context.rs` for formatting and truncation; patch handlers and workspace changes for edits; and history/persistence code to distinguish contemporary model input from saved traces.

### 6.2 Research questions and implementation locations

| Question | Main locations | Misinterpretation to avoid |
| --- | --- | --- |
| Did the test actually run? | Command handler, process manager, `exec-server/` | Equating a proposed command with execution |
| What did the model receive after failure? | `tools/context.rs`; Code Mode wrappers when applicable | Equating terminal display, logs, and model input |
| How did feedback enter the next request? | `session/turn.rs`, history management | Looking only at the final answer |
| What source or test files changed? | Patch handlers and actual workspace state | Missing shell-based edits |
| Was old feedback compacted or replaced? | Compaction and history code | Assuming early output remains verbatim forever |
| What can be persisted and resumed? | `thread-store/`, `rollout/`, `state/` | Treating session resumption as a full environment snapshot |

These are navigation and instrumentation starting points. Editing one file alone does not implement complete replay or feedback intervention.

### 6.3 Codex tests versus agent-generated tests

[core/tests/](https://github.com/openai/codex/tree/c260087efe8cc6dcc0526e7018ae9e0e3fc134e3/codex-rs/core/tests) tests Codex itself. Examples include [unified_exec.rs](https://github.com/openai/codex/blob/c260087efe8cc6dcc0526e7018ae9e0e3fc134e3/codex-rs/core/tests/suite/unified_exec.rs), [tools.rs](https://github.com/openai/codex/blob/c260087efe8cc6dcc0526e7018ae9e0e3fc134e3/codex-rs/core/tests/suite/tools.rs), and [compact.rs](https://github.com/openai/codex/blob/c260087efe8cc6dcc0526e7018ae9e0e3fc134e3/codex-rs/core/tests/suite/compact.rs).

Tests generated for a target project typically live in that project or a temporary directory and run through general command tools. The execution harness does not inherently know whether a self-written test's expected result matches the user's actual requirements. Interpretations and subsequent edits must be studied in the trajectory.

### 6.4 Do not transfer implementation assumptions across harnesses

The earlier Python trajectory study used mini-SWE-agent. Codex's truncation, context management, tools, and approvals cannot be assumed to describe those traces.

This guide supports instrumentation of future Codex experiments, understanding Codex feedback propagation, and comparisons across harnesses. Claims about existing mini-SWE-agent data still require the actual version and execution evidence from that experiment.

This guide documents source structure. It does not change the execution logic or report a new model experiment.
